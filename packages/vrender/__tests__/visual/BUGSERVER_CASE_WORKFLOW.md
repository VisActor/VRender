# BugServer Photo 用例协作

只有对应 BugServer 产品的项目管理员可新增平台用例；GitHub写权限、平台登录或报告读取权限不等于创建权限。无权限的贡献者提供复现材料，由管理员处理，不共享账号或令牌。本地Playwright与平台Photo是两套用例，不自动同步。

## 1. 提供材料并检查已有覆盖

按[本地用例指南](./cases/README.md)补充可复现测试，提供关联PR/issue、当前提交SHA、验证目的、固定公开数据、动作顺序、预期状态、本地用例路径与实际结果。管理员查找对应产品的已有目录和相似case，优先复用。未创建时在PR注明“待项目管理员补充”，不编造caseId。

## 2. 管理员创建并回读

本仓产品为 `canopus（VRender）`，规范GitHub仓库为 `VisActor/VRender`。管理员先核对产品、环境和自身权限，通过团队支持的平台或CLI创建。将场景适配为平台浏览器环境的JavaScript；不能直接上传含Playwright/Jest API的本地模块。保留必要动作和状态验证，等待资源及目标状态就绪后再请求截图；需要交互时按平台交互配置维护。

创建后保存真实caseId、目录、请求标识和返回链接，回读核对内容。创建成功只表示已保存，不代表已运行或已有标准图。结果未知时保留同一请求标识和输入，联系管理员回读原请求；不要换ID重复创建。公开仓库只保存可公开的材料、ID和链接，内部内容通过受限渠道交接。

## 3. 回填并在新版本验证

确认创建成功后，在相关本地用例的追溯注释及PR中填写真实ID，并提交必要的用例/说明变更，形成真实新版本。平台caseId仅供追溯，不建立同步关系，也不按PR填写的ID筛选Photo。

只有符合[正式准入范围](../../../../CONTRIBUTING.zh-CN.md#pr-检查与合入流程)的PR由工作流自动推进。Photo阶段冻结对应产品全部Photo用例及其交互；已冻结集合/旧批次不会因新增case扩容。刷新页面或重试旧批次不能证明新增case已执行。前置检查或构建受阻时先处理阻断，不手动另派批次冒充工作流结果。存量、fork、范围外或已合入PR，由管理员安排独立验证或后续真实变更PR。

## 4. 人工核查结果

在PR摘要关联的工作流和Photo报告中核对当前head/base、测试版本、原批次、真实caseId及其交互，确认执行终结后检查实际图、基准图、差异和错误。当前case内容不证明历史批次运行了该内容。无读取权限者由管理员提供可公开结论。

Photo保持report-only：差异、缺基准、错误、未完成状态如实保留，不阻断三项自动建议；流程completed不代表Photo全量通过。图片相似也不能替代本地语义断言。

## 5. 首次基准与后续更新

新case缺基准时先核对本轮执行成功、目标状态和测试图正确；缺图、执行错误和未完成结果不能采用。Approve/Merge不授权自动采用图片，工作流不自动建立或更新基准。

具有基准写权限的管理员另行取得本次更新授权，核对准确产品、case/interaction、报告及task，读取现有标准引用后按平台支持的条件更新执行；只在明确无基准时使用“无基准”条件，不能把未知当空或无条件覆盖。结果未知保留原请求标识与输入，回读恢复，不换ID。

共享基准不按PR、分支或commit隔离，修改影响后续测试。保存授权及回执，再安排新的Photo执行复验；设置成功不代表测试通过，原缺基准/差异报告保留。PR分别记录本轮测试事实、基准处理和未完成复验。
